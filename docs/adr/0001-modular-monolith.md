# ADR-0001 · 采用模块化单体而非微服务

- 状态：已采纳
- 日期：2026-11-08

## 背景

项目要移植 agpayplus 的 22 个业务切片和 15 个渠道，同时是个人练手项目，每周可投入约 15 小时。供体是单体架构，但分层弱、服务层是事务脚本。

目标是在不引入分布式复杂度的前提下，让代码具备"将来可拆"的结构。

## 决策

采用**模块化单体**：单进程部署，6 个模块（Payment / Refund / Transfer / Division / Access / Ledger）共享一个 `PaymentDbContext`，但模块之间只允许通过 Application 端口或领域事件通信。

模块内部严格分层：`Domain` 零外部依赖，`Application` 编排，`Infrastructure` 实现。

## 后果

好处：

- 只需一套部署、一个数据库，本地开发与调试成本最低。
- 模块边界以端口表达，将来拆服务时端口即拆分面。
- 可以在单进程内写端到端测试，反馈环比微服务快一个数量级。

代价与约束：

- 必须有纪律：禁止跨模块直接引用对方实体或 DbContext，否则"模块化"只是目录游戏。
- 共享 DbContext 意味着数据库层无法独立演进；接受这一点，拆分时再处理。
- 需要一个自动化的架构检查（P6）来防止依赖回退。

## 替代方案

- **微服务**：运维与分布式事务成本远超个人项目收益，否决。
- **单层单体（照抄供体）**：无法解决贫血模型与服务层事务脚本问题，否决。
- **模块化单体 + 多 DbContext**：边界更硬，但迁移与事务管理复杂度上升，暂不采用；若模块间出现写冲突再升级。
