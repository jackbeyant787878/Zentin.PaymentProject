## 1. 移植原则

### 1.1 器官移植，不是搬家

| 资产 | 规模 | 处置 | 理由 |
| --- | --- | --- | --- |
| 渠道适配层（15 渠道，354 个 `.cs`） | 约 3.4 万行 | **逐渠道重新移植**，只反转依赖 | 签名/验签/报文是钱，不能"DDD 化"；但也不能保留对应用服务的反向调用 |
| 领域实体 / 仓储 / 应用服务（22 切片） | 大 | **按语义重写**，供体代码当规格 | 旧代码是贫血模型 + 服务层事务脚本，直接搬会继承旧问题 |
| 宿主与管道（Base.Api、4 个 API 宿主、JWT、Swagger、Serilog、EF 生成模型） | 中 | **丢弃**，用平台能力替换 | 平台已有网关/身份/日志 |

### 1.2 三条不可协商的规则

1. 供体 commit 锁定 `ba61fea9cbbcd1c6940e5b3ef8b55284e2ab3eac`，不做 `git pull`。
2. 不建第三个项目。Zentin 是唯一宿主。
3. 每完成一个切片必须更新 `03-module-inventory.md` 与 `06-ai-coding-playbook.md` 的度量表。

### 1.3 为什么可以这样并行

学习速度取决于**反馈环密度**，不是代码量。支付主链的每个切片都有确定性输入输出、可写黄金测试、可对照供体行为——这是最适合练 AI 协作的形态。渠道层是 15 个近乎同构的任务，适合用来练"模板复制 + 批量验证"。

## 4. 垂直切片模板（10 步）

每做一个切片，严格按此顺序。**不要跳步，不要并行做两个切片。**

1. **读供体**：定位对应服务与实体，产出行为清单（每条带 `文件:行号`）。
2. **写契约**：`docs/slices/<slice>.md`，含命令/查询契约、校验规则、状态迁移、幂等键、领域事件。
3. **Domain**：聚合 + 值对象 + 枚举 + 领域事件 + 领域异常 + 不变量单测（红）。
4. **Domain**：`I<X>Repository` 端口，只暴露实体/只读集合/分页结果。
5. **Infrastructure**：`<X>EntityTypeConfiguration` + DbSet + 迁移。
6. **Application**：Command/Query + Handler + Validator + 映射。
7. **Api**：端点 + 权限码 + 统一响应 + 异常映射。
8. **测试**：仓储集成测试（真实 SQL Server）+ Handler 测试 + EF 模型守卫。
9. **对照**：与供体行为逐条比对，差异写入契约文档的"差异"小节。
10. **写回**：更新 `03-module-inventory.md`、必要的 ADR、`06` 的度量表。

每步结束都跑：

```bash
dotnet build Zentin.Payment.slnx --nologo
dotnet test Zentin.Payment.Domain.Tests/Zentin.Payment.Infrastructure.Tests.csproj --nologo -v q
```

## 5. 渠道轨道（与主线并行）

原则：**每周最多 2 个渠道**，不与主线抢同一周的注意力。

| 批次 | 周 | 渠道 | 主要验证点 |
| --- | --- | --- | --- |
| B1 | W3 | 微信 `wxpay` | SPI 是否够用；V3 证书与验签；JSAPI/Native 两种 WayCode |
| B2 | W8 | 支付宝 `alipay` + 2 个 B2 | 与微信的抽象差异（RSA2、异步通知格式） |
| B2 | W9-W10 | 剩余 B2 | 模板复制成本 |
| B3 | W11-W13 | 8 个 B3 | 批量移植的吞吐与一致性 |
| B4 | W14 | PayPal `pppay` | 异构 SDK、币种、webhook 验签 |

每渠道必须包含 6 个动作：下单 / 回调 / 查单 / 关单 / 退款 / 退款回调。

**fixture 脱敏规则**：密钥、证书、卡号、身份证、签名体只保留摘要（前 4 位 + 长度），原始报文不入库。

| 风险 | 概率 | 影响 | 应对 |
