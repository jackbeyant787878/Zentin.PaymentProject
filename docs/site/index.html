The product

Full-link payment capability.

The platform references the complete business scenarios of the open-source AgPayPlus project, then models them from scratch. It is not a code migration, a version upgrade or a refactor of the old system.

01

Merchant management

Merchant onboarding, application access, rate configuration, permissions and business statistics across a three-tier ISV / agent / merchant hierarchy.

02

Multi-channel transactions

Order creation, cashier interaction, channel routing and callback processing, driven by an explicit order state machine.

03

Refunds

Refund records as their own aggregate, with channel refund callbacks and idempotent retry handling.

04

Split settlement

Receiver binding, profit-sharing rules, automatic split accounting and agent fund settlement.

05

Transfer & notification

Fund transfer plus asynchronous merchant notification, delivered reliably through the event bus.

06

Reconciliation

Channel bill import, difference detection and periodic clearing, scheduled through the distributed task service.

Domain boundaries

Four services, four domains.

Each service inherits a mature business boundary from the legacy system and is rebuilt to the same four-layer DDD specification. Services carry no authentication logic — that lives entirely at the gateway.

PAYMENTSERVICE

Core payment domain

Order creation, channel payment, callback parsing, state machine transitions, refunds and notification scheduling.

MERCHANTSERVICE

Merchant domain

Merchant settlement, profiles, application access, rate configuration, permissions and data statistics.

AGENTSERVICE

Agent profit-sharing domain

Agent hierarchy, profit-sharing rules, revenue statistics, automatic split settlement and agent fund accounting.

MANAGERSERVICE

Platform management domain

Platform configuration, channel management, payment parameters, global order management and risk-control settings.

Design principles

What the architecture guarantees.

01

Domain layer, zero dependencies

Aggregates, value objects, domain events and specifications are pure business logic. Fund rules and state machines stay decoupled from databases and middleware, so they remain testable on their own.

02

CQRS read / write separation

High-concurrency transaction writes and high-frequency order queries are separated, resolving the performance conflict inherent to payment workloads.

03

Event-driven decoupling

PaymentSucceededEvent is published to the RabbitMQ bus; downstream services consume it asynchronously. No hard-coded cross-service dependencies.

04

Gateway-centric security

OpenIddict only issues tokens. YARP performs stateless JWT public-key verification, signature checks and permission validation, so business services never see authentication code.

05

Money handled precisely

Amounts are integer cents; rates are fixed-precision decimals. Binary floating point never touches a monetary calculation.

06

Cloud-native by default

Independent Docker images, stateless deployment, GitHub Actions delivery and K3s today — fully compatible with standard Kubernetes tomorrow.
